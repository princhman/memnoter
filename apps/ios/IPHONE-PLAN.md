# iPhone adaptation research

Date: 2026-11-08. Status: implemented with verification limitations recorded below.

## Required outcome

Ship one universal iPhone/iPad app using the current SwiftUI host, embedded web editor, shared review implementation, Rust core and sync. All existing iPad functionality must remain accessible on iPhone. Preserve the iPad's general appearance and interactions. The user subsequently authorized a shared Contents/focus redesign on both platforms, replacing the standalone cursor-dependent focus control.

## Recommended approach

Extend the existing navigation split view rather than introduce a separate app, tab navigation or a second editor. Apple documents automatic collapse to a native navigation stack and an explicit compact-column binding for programmatic navigation. Column visibility alone does not control a collapsed split view. [NavigationSplitView](https://developer.apple.com/documentation/swiftui/navigationsplitview)

Keep the current iPad split-view configuration. If phone-specific configuration requires extracting a small navigation wrapper, share its sidebar and detail content and retain session ownership above the wrapper. Do not duplicate feature logic. The fallback, only if the navigation spike exposes an unresolved platform problem, is a phone-only NavigationStack over the same content and session.

Use a phone idiom check for changes exclusive to iPhone, then available width/height to fit that phone interface. A compact size class or CSS media query alone also matches narrow iPad windows. Existing iPad width-dependent behavior must continue unchanged. Apple's layout guidance supports adapting to available window space; the additional phone boundary follows this project's preservation requirement. [Layout guidance](https://developer.apple.com/design/human-interface-guidelines/layout)

## Changes identified in this repository

- `project.yml`: change device family from `2` to `1,2`; add explicit iPhone orientations. Keep the bundle identifier, data locations, minimum iOS 17 deployment target and core package. Inspect generated build settings and app icon coverage.
- `RootView.swift`: introduce phone compact-column state. Phone list selections and programmatic opens must reveal the destination; Back and edge-swipe must return to the list. Preserve iPad column visibility and its saved sidebar preference.
- Navigation currently routes selection through asynchronous `navigate`, which flushes and opens before committing `selected`. Verify actual SwiftUI selection behavior with that delayed commit. A failed flush/open must retain the previous destination and editor state; do not set the phone column to detail before the operation succeeds.
- Audit every route: module row, Recent, search result, creation, global/module review, review-to-note reveal, deletion, remote deletion, restore and launch restoration. Existing `editReviewCard` changes selection independently of `navigate` and needs the same phone presentation behavior. Returning to the list must not clear the saved destination or destroy the editor.
- Gate custom Show/Hide Sidebar controls off on phone and retain native Back navigation. The current sidebar-hiding action is ineffective as a phone navigation mechanism because it only sets column visibility.
- Phone editor toolbar: reserve space for Back, undo/redo, title and the action menu. The whole-note title opens Contents directly. While focused, the title menu contains the current path, whole-note/ancestor navigation and Contents, without repeating the selected location. The ellipsis contains editing, focus-entry and review actions. Keep iPad toolbar items, ordering, spacing and material unchanged.
- Phone focus lives in the navigation title: note-name dropdown normally, section name and direct × exit while focused, without a subtitle. Phone paragraph styles use one menu at the start of the formatting row. Both additions are gated to phone idiom.
- `FormattingBar.swift`: reuse the current horizontal scrolling row and pinned keyboard-dismiss button. Validate its narrow viewport and link entry before changing it. The link editor currently forces a popover; use a phone sheet if it cannot fit above the keyboard, preserving the iPad popover.
- `ContentsPopover.swift`: already requests compact sheets and medium/large detents. Verify phone layout and dismissal; do not globally change its current width or iPad presentation. SwiftUI offers explicit compact presentation adaptation. [PresentationAdaptation](https://developer.apple.com/documentation/swiftui/presentationadaptation)
- `ReviewView.swift`: already has narrow toolbar behavior and a two-column rating grid below 640 points. Validate title/count/button space, long card content and Dynamic Type; preserve iPad thresholds and styling.
- `HomeView.swift`: keep the existing home on iPad. On phone, consider hiding the keyboard-shortcut reference while retaining all features in touch controls.
- `SettingsView.swift` and `SyncSettingsView.swift`: reuse native lists, pickers, confirmation and error flows; validate small-screen wrapping and keyboard access.

## Embedded editor boundary

Keep `WebSession` and its persistent `WKWebView`, the existing bridge, custom asset/file schemes, view persistence and serialized open/flush. `WebSurface.makeUIView` already returns `session.web`. Do not recreate it on selection, Back navigation, rotation or SwiftUI updates; never attach the same web view to two simultaneous surfaces. UIKit view integration remains supported through UIViewRepresentable. [UIViewRepresentable](https://developer.apple.com/documentation/swiftui/uiviewrepresentable)

Retain the current scroll ownership: HTML owns scrolling; native web scrolling is disabled and automatic content inset adjustment is off. The host already reports keyboard overlap and safe-area information to the editor. Check this pipeline on phones before adding another inset mechanism, which could cause double spacing or competing caret scrolling.

The editor already uses `viewport-fit=cover` and `env(safe-area-inset-*)`. WebKit documents these primitives for avoiding display cutouts and the home indicator. They are a foundation, not evidence that this app is correct on current phones. Verify landscape cutouts, keyboard transitions and image-preview close controls on-device. [WebKit safe-area guidance](https://webkit.org/blog/7929/designing-websites-for-iphone-x/)

If embedded UI needs phone-only adjustments, inject an explicit phone marker at document start and scope CSS to it plus viewport dimensions. Do not change generic `.tiptap`, review padding, shared breakpoints or shared editor styles to solve a phone-only problem. Check tables, math menus, image resize/crop/occlusion, card menus, text selection and link entry; these use shared web UI with their own geometry.

## Implementation and acceptance sequence

1. Capture the existing iPad baseline before app changes, using deterministic note/review content. Include light/dark, portrait/landscape, sidebar open/closed, keyboard hidden/shown, Contents, section focus, image preview and a narrow window where supported. Record device, orientation, text size and keyboard conditions so comparisons are meaningful.
2. Enable iPhone and make a minimal navigation spike. Exercise delayed selection, native Back/edge-swipe, same-row reopening, Recent, create, search, review-to-note, restoration and failed-save handling. Resolve navigation ownership before polishing layouts.
3. Add only demonstrated phone layout/presentation fixes, preserving iPad branches and shared session/data logic.
4. Exercise the full feature inventory on the retained small phone and large phone: editing/formatting, all card types and section tools, images, tables, math, search, review/undo/redo, sync including images/conflicts/offline recovery, settings, backup/restore and relaunch persistence. Verify caret/selection and the software keyboard in both orientations; include large text and VoiceOver. Simulator checks do not replace a physical-phone pass for keyboard/selection and Photos behavior.
5. Rebuild and compare iPad screenshots under the baseline conditions. Require unchanged geometry, typography, toolbar composition, materials and presentations, allowing only nondeterministic content/system rendering. Repeat iPad editing/navigation/review and save checks. A successful phone build does not establish preservation.

Use only the retained simulator pool and device-panel workflow from AGENTS instructions. Do not reset retained app data for fixtures. Current research did not boot, install or operate any device.

## Shared Contents/focus redesign

The later request supersedes the earlier flat Contents and toolbar-focus designs on both platforms. Contents now browses one heading level per page, with native Back navigation and document-wide section search. Each row has a direct Focus/Unfocus button; the reading section and its ancestors are highlighted without checkmarks. Browsing is separate from focusing. Parent pages offer Go to section; leaf rows navigate directly. Whole note appears while focused and exits focus from any page. Standalone focus controls and the ellipsis focus-entry action are removed. The focused section name remains in navigation, with the phone's quick × exit retained.

The bridge now sends a full outline alongside the visible outline. The full tree includes folded and focused-out headings; visible headings still own reading-position tracking. Contents navigation reveals hidden targets and exits focus only when necessary. Direct focus unfolds its target and folded ancestors without clearing unrelated folds. Tree construction uses document order and heading IDs, with immediate-child lookups and lazy native lists.
